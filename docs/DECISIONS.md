**C-001 · Git branch** — The cloud harness started the session on `claude/nice-turing-2470ze`; the brief (D10) and kickoff prompt say work on `main`. Decision: work on `main` (identical commit at start) and push there; if `main` pushes are rejected, push the session branch and note it in STATUS.md. Why: the owner's explicit instruction in the kickoff prompt.

**C-002 · Model fetching** — Context: BRIEF §13 wants pinned, verified, resumable, per-group downloads. Alternatives: pure-bash TOML parsing; a Rust xtask; Python stdlib helper. Decision: `scripts/fetch-models.sh` → `scripts/fetch_models.py` (stdlib only, `curl -C -` for resume, `tomllib`, SHA-256 + size verification). Why: Python 3.11+ is on both the cloud VM and the Mac; no extra deps; bash TOML parsing is brittle. Whisper/VAD/eval hashes were taken from HF LFS metadata of the pinned revision and are re-verified on every download; PocketTTS hashes match BRIEF §3.2 exactly (all 12 files verified).

**C-003 · FLEURS subset** — Context: FLEURS parquet files are 400–800 MB per language with a single row group. Decision: `scripts/fleurs_subset.py` reads the pinned parquet through `HfFileSystem` range reads and extracts 10 utterances (5–20 s) per language; ≈ 7 min total, nothing large stored. FLEURS is generated, never committed (CC-BY-4.0 attribution in About later).

**C-004 · TTS parity test-set budget (cloud, 4 vCPU)** — Context: BRIEF §6.1 asks for all 10 voices on short+medium texts, 3 samples per (text, voice), long text on 3 voices; the reference runs at RTF ≈ 1.2 on this VM. Decision: 11 short/medium/special texts + 1 long text (1 457 words, ≈ 8–9 min of audio; BRIEF says ~1500). All 10 voices × 3 samples on s1,s2,m1,m2; george/alba/michael × 3 samples on s3,s4,m3,m4,n1,q1,l1; the long text on george/alba/michael × **1** sample (3 samples would add ≈ 3 h per engine). Bulk WER ASR is Whisper `small` (turbo ≈ 36 s per 30 s window on this CPU would make 400+ clips take > 4 h); a turbo cross-check on a subset is added where time allows. Gates are relative so the ASR choice cancels; this is noted in the report.

**C-005 · Candle PocketTTS port — what the 2.1.0 weights required** — Context: the `pocket-tts` 0.6.2 crate (babybirdprd, MIT OR Apache-2.0) targets the older `b6369a24` model. Findings: (1) the 2.1.0 `english` weights have `inner_dim=32` in Mimi's downsample and `speaker_proj_weight [1024,32]`; (2) the ten voice files are **serialized KV-cache model states** (`transformer.layers.N.self_attn/cache` `[2,1,T,16,64]` + `offset`), not `audio_prompt` latents; (3) the crate's text chunking/padding differs from Python 2.1.0 (`split_into_best_sentences` is token-boundary based, no 8-space padding for `english`, `max_gen_len = ceil((tokens/3+2)·12.5)`, `frames_after_eos = guess+2`); (4) the crate drags in `hf-hub`, `intel-mkl-src`, `tokenizers/http` (network-capable). Decision: vendor + patch (`spike/tts-rust/vendor/pocket-tts`, PATCHES in its README): local-path-only weights, KV voice-state loader, inner_dim support, Python-faithful chunker (verified identical chunks on all test texts incl. the 62-chunk long text), no hf-hub/MKL. Speed: the crate decodes Mimi serially (RTF 1.5); the Python reference overlaps decode in a thread, so the Candle path now pipelines flow-LM and Mimi on two threads (RTF 1.0 vs reference 1.2 on this VM).

**C-006 · Audio decode stack** — symphonia 0.6.1 (all codecs/formats) + `symphonia-adapter-opus-rs` (pure-Rust Opus, no libopus/cmake) + own MP4 `elst` reader (symphonia's isomp4 is not gapless: AAC priming leaked +46 ms). All 21 fixture formats decode within ±50 ms of the source and match its content (lossless: correlation ≥ 0.99). **MKV/AAC** gets ±100 ms because Matroska carries no AAC priming/padding info (unknowable by any decoder; documented in the test). AVFoundation fallback stays a Mac item.

**C-007 · Recorder design** — One SPSC ring per stream session (a rebuilt stream gets a fresh ring; the writer drains the old one first, so no samples are lost at the switch). Pause closes the stream (mic indicator goes off, no samples buffered). Default-device following polls `AudioInput::default_device_id()` once per second *only while recording* (cpal 0.18 itself auto-reroutes default-device streams and reports `ErrorKind::DeviceChanged`; the Mac session must verify that the two don't fight — MAC_HANDOFF #4). File format fixed to the first device's rate; later devices are resampled (rubato). WAV header is patched in place + fsync every 2 s (`sync_interval`), measured loss on `kill -9`: 1.2 s. Recordings >≈4 GB (≈ 12 h at 48 kHz) stop gracefully (classic RIFF limit) — RF64 left for "Later".

**C-008 · whisper-rs abort callback** — Context: whisper-rs 0.16.0's `set_abort_callback_safe` double-boxes the closure, so whisper.cpp reads garbage and aborts every run with error −6. Alternatives: pin an older whisper-rs; patch the crate; avoid abort support. Decision: our own `extern "C"` trampoline over an `AtomicBool` using `set_abort_callback` + `set_abort_callback_user_data` (in `stt/whisper.rs`). Why: cancel must stop a 30 s window within ~1 s, and the unsafe surface is 15 lines we test (`stt_pipeline` cancel test).

**C-009 · STT: normalize before gating** — Context: the first STT bench reported 70 % English WER on FLEURS. Cause: FLEURS contains very quiet speakers (peak 0.005–0.01, ≈ −45 dBFS) and our absolute energy gate + Silero's fixed threshold dropped them (33.9 s of 104.9 s kept). Alternatives: lower the thresholds only; per-file gain; per-chunk gain. Decision: peak-normalize every transcribe/language-ID chunk (target 0.5, ≤ +40 dB, never above the noise floor 0.0015) and level the VAD's analysis copy in 1 s blocks (`filters::normalize_peak`, `level_for_vad`); gate thresholds lowered accordingly. Why: loudness varies far more than a fixed threshold can express; silence/noise/tone fixtures still yield 0 hallucinated characters (tested). Result: speech kept 33.9 s → 81 s, words 63 → 213 (reference ≈ 200).

**C-010 · IPC types & typed bindings** — Context: BRIEF §5.4 wants typed IPC. Decision: `tauri-specta =2.0.0-rc.25` with `specta-typescript 0.0.12` generates `ui/src/bindings.ts` from the Rust DTOs (`cargo test -p parlo-app export_bindings`, also at debug startup). specta forbids `u64`/`usize` in TypeScript, so millisecond/byte fields are annotated `#[specta(type = specta_typescript::Number)]` (values stay far below 2^53) and `Option<Option<T>>` patches are expressed as plain `Option<T>` + conventions (`input_device: ""` = system default; `clear_transcript`/`clear_tts` flags). Alternatives: hand-written TS types (drift), ts-rs (a second type system), JSON-schema codegen. Why: one source of truth, compile-time checked on both sides.

**C-011 · UI structure** — Pinia setup stores (`app`, `recorder`, `transcribe`, `speak`, `toast`) own all state machines; components are thin. All native access goes through one `Backend` interface (`ui/src/backend/types.ts`) with a real adapter over the generated bindings and a mock with scripted engines (`VITE_MOCK_BACKEND=1`) that honours the same contract (`contract.test.ts`). No UI kit, no icon package (inline SVG set), no web fonts; the app's only timers are one-shot (toasts, debounce) or exist while a countdown is visible (status chip). In the real app the native menu owns ⌘-shortcuts (they come back as `menu:action`) so key presses aren't handled twice; the mock/browser build maps them itself.

**C-012 · TTS runtime = Candle port of PocketTTS (gate PASSED)** — Context: BRIEF §6.1 parity gate, cloud part (relative CPU metrics; machine: 4 vCPU Xeon 2.8 GHz AVX-512, no GPU). Alternatives: Python sidecar (fallback only if no candidate passes), `sherpa-onnx` PocketTTS (voice cloning from reference WAVs → voice drift; extra runtime), PocketTTS.cpp — the latter two were **not evaluated** because candidate 1 passed every gate with margin (the procedure adopts the first that passes). Decision: vendored + patched `pocket-tts` 0.6.2 (Candle, CPU; `tts-metal` feature for the Mac) behind `TtsEngine`. Numbers (183 short/medium/special files + 3 long per engine, 3 samples per text×voice): WER (Whisper small round trip) 2.50 % vs reference 2.11 % (+0.39 pp, gate +2); speaker-embedding cosine cand↔ref ≥ intra-ref − 0.05 for 10/10 voices (e.g. george 0.851 vs 0.851 intra-ref); warm RTF 0.972 vs 1.256 (−23 %, exclusive alternating run, 33 jobs each, σ 0.03/0.04); TTFA median 307 vs 389 ms; cold load 0.54 vs 1.40 s; peak RSS 641 MB vs 956–1174 MB; artifacts clean (0 NaN, clip ≤ 0.009 %, no silences > 2 s, duration/word ratio 0.91–1.15). Why: all gates pass, the Rust engine is smaller and faster than the reference, and it removes Python from the shipped app. Open: the Mac phase confirms TTFA ≤ 500 ms, cold load ≤ 3 s and CPU-vs-Metal (MAC_HANDOFF A1); the owner's blind listening (`spike/tts-parity/listen.html`) is non-blocking — switching engines is a one-line change. Details: `spike/tts-parity/report.md`.

**C-013 · STT default = large-v3-turbo q8_0 + Silero VAD** — Context: BRIEF §6.2, FLEURS (8 languages) + synthetic + edge files through the production pipeline (after the C-009 fix). Alternatives measured: turbo q5_0 / f16, small (f16, q8_0). Result (mean FLEURS WER): turbo-q8_0 6.8 %, turbo-f16 6.8 %, turbo-q5_0 6.7 %, small-q8_0 19.3 %, small-f16 21.4 %; 0 characters hallucinated by the pipeline on silence/noise/tone for every variant tested (raw whisper without VAD: 7–21 chars); FLEURS language ID 8/8 (small-q8, turbo-q8). Decision: turbo q8_0 (as the brief expected) — accuracy equals f16 at 64 % of the RAM and is faster than q5_0 on CPU; q5_0 is the lean alternative if the Mac shows a RAM problem (MAC_HANDOFF A2). Why not small: 3× the WER, 5 languages of the owner's set would be unusable. Details: `spike/stt-bench/report.md`.

**C-016 · App bundle fixes found on first Mac build** — (1) ggml-metal needs `___isPlatformVersionAtLeast`; Rust links with -nodefaultlibs and Homebrew's compiler_builtins targets macOS 26, so `src-tauri/build.rs` links `libclang_rt.osx.a`. **C-017 · `MallocLargeCache=0` (memory back to baseline after a job)** — Context: after a TTS+STT job and the idle unload the main process kept 580–614 MB (target baseline +30). Both engines were dropped (`is_loaded()==false`); `vmmap` showed `MALLOC_LARGE (empty)` ≈ 480 MB dirty, and `malloc_zone_pressure_relief(NULL,0)` returned 0 MB. Reproduced without the app (`cargo run --release -p parlo-core --example memtest --features tts-accelerate`: 6 → 439 → 490 MB, still 490 MB after `drop(engine)`). Alternatives: mimalloc as global allocator (no change: the STT side is C++ malloc, and TTS did not improve either), relief on every zone (0 MB). Decision: libmalloc’s large-block cache is switched off with `MallocLargeCache=0` (undocumented env var read at the first allocation): `Info.plist` `LSEnvironment` for LaunchServices launches, plus a one-time self re-exec (same PID) in `main.rs` for any other launch. Result: memtest 490 → 89 MB; bundled app after-job − reopened = **+20 MB** (target ≤ +30). Cost: large allocations are mapped/unmapped each time (only model load/job start; no measurable speed change).

Alternatives: keep 2 s and widen the test; sync every 1 s. Decision: `RecorderConfig::sync_interval` default 1 s (one header patch + fsync per second is negligible). Result: 1.0 s lost, twice; recorder/kill9 tests still pass.

**C-021 · Product principle: offline by default; the only network use is a download you start (Transcribe from URL)** — Context: the owner wants to transcribe a YouTube video, a podcast episode (RSS enclosure `.mp3`/`.m4a`) or anything yt-dlp supports. Owner's wording: *"Parlo does not rely on the internet and never sends user data to any service. Pulling content from the internet as an optional feature the user starts is fine."* This supersedes BRIEF G6 / §5.2 principle 3 / the "Don't" list ("zero outbound network connections", "no runtime network feature") — those now read "offline; the only network use is a URL download you start; nothing is ever uploaded". Decision: (1) The **only** outbound traffic is a download the user starts (paste/⌘V/drop a link + Transcribe). No telemetry, no updater, no background requests, no "check for updates" of yt-dlp (`yt-dlp -U` would modify the signed bundle; updating = a rebuild with a new pin, or `brew upgrade yt-dlp` for the system copy). (2) The **Parlo process itself never opens a socket**: all networking happens in a child process — yt-dlp, or `/usr/bin/curl` for a plain audio file — started in its own process group (cancel and quit kill the group). No HTTP-client crate was added to Parlo (the `url` crate added to `parlo-core` is a string parser only). (3) The webview CSP is unchanged (`connect-src 'self' ipc: http://ipc.localhost`; the webview never touches the network; a pasted/dropped link is just text that goes to the core). (4) Settings → Downloads → "Allow downloads from URLs" (default **on**); off hides the URL card and makes `transcribe_start(url)` and `downloads_info` refuse (`download_disabled`). (5) Cookies (`--cookies-from-browser`, default **off**) are read locally by yt-dlp and sent only to the site being downloaded from; the picker lists only browsers installed *and* with a profile on this account. Verification: `scripts/check-offline.sh` — every existing flow still runs inside `unshare -rn` and the sampled Parlo PID has 0 inet sockets (2 301 samples); for a URL job (real app command layer, real yt-dlp, local HTTP server) `scripts/sample-sockets.py` shows 0 inet sockets in Parlo's own PID and loopback sockets only in the downloader child (positive control). Alternatives: an HTTP client in Rust (reqwest/ureq — rejected: puts networking, TLS and cookie handling inside the product process and breaks the "Parlo itself never connects" invariant); a Python sidecar (rejected: BRIEF §16 "no Python"); yt-dlp only (rejected: a plain `.mp3` link must still work when yt-dlp is broken or missing → curl fallback). App Sandbox (BRIEF D5 "Could"): an App-Sandbox child inherits the sandbox, so downloads would need `com.apple.security.network.client`, which defeats D5's "OS-enforced offline" — D5 is now moot unless the owner wants to drop the feature. The entitlements keep **no** network entitlement (the app is not sandboxed, so none is needed).

**C-022 · Downloader: pinned yt-dlp (bundled) → system yt-dlp → curl; flags; JS runtime; onedir vs onefile** — Context/findings (yt-dlp **2026.08.19**, the newest stable on PyPI/GitHub on 2026-10-18; official standalone builds pinned by version + the release's own SHA-256, `tools/manifest.toml`, `scripts/fetch-tools.sh`, binary never committed; Linux x86_64/aarch64 and macOS universal2, both onefile and onedir pinned): (1) **JS runtime** — `--help` of the pinned build: YouTube's JS challenges need an *external* runtime; supported in priority order deno, node, quickjs, bun; **only deno is enabled by default**; the challenge-solver scripts (EJS) are bundled in official executables ("`--remote-components` … not needed if you are using an official executable"), so Parlo never passes `--remote-components` (it would fetch from npm/GitHub at run time). The standalone binary does not contain deno. Decision: **do not bundle deno**. A GUI app has no shell `PATH`, so Parlo searches (Settings override for yt-dlp only), `/opt/homebrew/bin`, `/usr/local/bin`, `~/.local/bin` (then `$PATH` for dev) and passes `--js-runtimes deno:<path>` when deno is found and the binary's version is ≥ 2025.11.12 (the release that introduced the option — from memory, not re-verified; the pinned build does have it; an older system yt-dlp that rejects the flag just fails over to the next downloader). If YouTube still fails with the bundled build, the system-yt-dlp fallback covers it (Homebrew's yt-dlp depends on deno). The Settings page shows whether deno was found. Node/bun/quickjs support is *not* used (spec: deno only). (2) **Flags** — `--no-config` (never read the user's global config), `--no-playlist --playlist-items 1` (only the single item, also for a pure playlist link), `--no-warnings --no-mtime --cache-dir <Parlo cache> --socket-timeout 30`; probe `-J` first (title, duration, live/upcoming/post-live → refused *before* downloading, "no audio", all-DRM, disk-space estimate); download `-f "bestaudio[ext=m4a]/bestaudio" --newline --progress-template "download:PARLO_DL status|downloaded|total|estimate|speed|eta"` (parsed line by line, no polling), `-o <job>/.dl/media.%(ext)s`, URL after `--`; never `-x`/post-processing → **no ffmpeg**. Impersonation `--impersonate chrome` only if `--list-impersonate-targets` shows an *available* Chrome row for that binary (else skipped + a log warning; the pinned build has Chrome targets via curl_cffi); cookies `--cookies-from-browser <known name>`; rate limit `--sleep-interval 5 --max-sleep-interval 15` (yt-dlp sleeps before *each* download, the first included — verified against the real binary: `[download] Sleeping 1.68 seconds ...` on stdout, shown as "Waiting N s"). (3) **Fallbacks** — bundled → one automatic retry with the system yt-dlp (UI: "Bundled downloader failed, retried with system yt-dlp") → `/usr/bin/curl` for direct media links only (Content-Type `audio/*`, or `application/octet-stream`/`video/mp4` with an audio file name/extension; `text/html` is never audio) → otherwise "Couldn't download this link. Install or update yt-dlp: `brew install yt-dlp` / `brew upgrade yt-dlp`." with every tool's output in "Show details". Only extractor/format/HTTP-class failures fall through; verdicts about the link (live, private/age/login, DRM, no audio, 404, no network, disk full, cancel) end the chain with their own message. Found while testing with the real binary: impersonated (curl_cffi) transport errors read `Failed to perform, curl: (7) Failed to connect…`, not `Connection refused` — the classifier knows both; `-J` prints `null` on stdout when it fails (exit 1). (4) **Decoder** — no ffmpeg means the file is whatever YouTube/the site serves: AAC in fragmented MP4 (itag 140, `moof` boxes, unknown duration), WebM/Opus (itag 251), MP3. All four shapes decode within ±50 ms (new fixtures `fixtures/generated/url/*`, `decode_formats.rs` `url_*` tests); no decoder change was needed. (5) **onefile vs onedir** (the brief: measure, then decide) — Linux x86_64, 4 vCPU, `--version` median of 5: onefile **1.09 s**, onedir **0.45 s** (`--list-impersonate-targets`: 1.12 vs 0.63 s); size: onefile 40.4 MB, onedir 40.5 MB zip / **92 MB** unpacked (macOS: onefile 37.1 MB, onedir zip 53.9 MB). A download runs ~4 child launches (version, impersonate list, probe, download), so onedir saves ≈ 2.5 s per job on Linux. Decision (**provisional**, no Mac measurement yet): **onedir**, in `Contents/Helpers/yt-dlp/` — faster, no per-launch self-extraction into `$TMPDIR` (which also sidesteps hardened-runtime trouble with freshly extracted unsigned libraries), and every Mach-O in it is signed with the app. The resolver and `fetch-tools.sh --variant` support both; the Mac pass (MAC_HANDOFF "Transcribe from URL") measures both and may flip `PARLO_YTDLP_VARIANT`. The helper has its own entitlements file (`disable-library-validation`, `allow-unsigned-executable-memory`; scoped to the helper).

**C-023 · Download storage, recovery and hygiene** — Context: "never leave a half-written file in the pipeline's input"; "quit or crash mid-download: throw away the partial file, the URL stays filled in". Decision: audio is fetched into `<data>/downloads/<id>/.dl/` (yt-dlp keeps its own `.part` until complete) and only a *finished* file is renamed to `<data>/downloads/<id>/audio.<ext>` (+ `meta.json` with link/title/duration) — the pipeline never sees anything else. The job request (`jobs/url-<hash>/request.json`) has an empty `path` until the download completes, so a quit/crash mid-download leaves nothing resumable; the launch-time **orphan sweep** deletes every `downloads/*` directory that is not the current transcript's (or a resumable job's) audio, any `.dl`/`.tmp` leftovers, and URL job dirs that never finished. The link survives in the workspace (`pending_url`, set when a download starts, cleared when the audio is on disk or on an explicit cancel) and refills the field on launch → retry is one click; errors keep it too. Once the download completes, the existing checkpoint/resume/recovery banner apply unchanged (the request points at the kept file). The audio is **kept while it is the current transcription** (mini player, re-transcribe in another language — which takes the `Path` branch and recognises the downloads directory, no second download — and export) and deleted when that transcript is replaced, cleared ("New") or its fresh download is cancelled; "Save audio" offers *as downloaded* (byte copy) or WAV/M4A/MP3 (decode → mono WAV → existing encoders).
